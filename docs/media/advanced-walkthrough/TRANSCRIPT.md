## 02. When the project outgrows the chat

Projects outgrow individual chats. Objectives change, files move, and another session must continue. System X began by keeping local scripts and TODOs consistent. It now retains the plan, current work, evidence, and next step.

## 03. A headless coordination layer

Think of a headless coordination layer: externalized context, reviewed memory, and visible decisions. The model still needs to read those records. The host supplies tools and permissions. Continuity comes from selected evidence and disciplined handoffs, without changing model weights.

## 04. Turn the idea into accepted work

Start with an outcome someone can accept. Define milestones, useful phases, and dependency-ready tasks. Keep one canonical ledger with owners, acceptance, evidence, and next actions. The CLI selects ready work and prepares bounded packets. Expand useful work, rather than thousands of empty tasks.

## 05. A rich brief. A bounded follow-up.

The first prompt explains the audience, constraints, sources, tools, and acceptance criteria. Later prompts select the task, revision, scope, and next check. Full copyable examples accompany this film. More information helps when it is relevant, verified, and accessible.

## 06. Agent 0 and native subagents

In a Codex app workflow, Agent Zero coordinates the accepted plan. App-native subagents can handle independent UI and test work with distinct write scopes. Their execution comes from the app. System X retains assignments, dependencies, results, and checkpoints.

## 07. Agent Y: the external CLI lane

Agent Y carries an authorized task into a separately installed CLI, such as Codex. It uses an owned Git worktree and task branch, retaining evidence. Opted-in draft pull requests return work for review. Acceptance, separately authorized merge, and verified cleanup remain distinct. A worktree is not an operating-system sandbox.

## 08. Agent X: time and interruptions

After an interruption, Agent X retains observed events, original times, revisions, and evidence. Inspect actual processes and remote state before retrying. Preserve uncertainty and resume from a bounded next action. A schedule record tracks a due item; it does not execute a job.

## 09. Agent Z: repeatable evidence review

Finishing execution creates a review candidate. Agent Z presents the same hundred questions for its policy version and scores supplied answers. Keep original evidence, unknowns, and decisive checks that can fail on bad inputs. The score is advisory. Agent Zero or the user records acceptance against task criteria.

## 10. ROOT: three TODO surfaces

The harness and an optional bot may show different task lists. ROOT binds saved observations to canonical task IDs and reports the delta. Agent Zero reconciles differences through actual tools and reads changes back. Matching observations do not establish continuous live synchronization.

## 11. Agent Alpha and AUTOBOT

Detailed projects need richer references. Agent Alpha selects relevant design, brand, research, rules, media, or data context from ten AUTOBOT functions. Source fingerprints support unchanged-request reuse. These are selected references, not ten running models or another task ledger.

## 12. DATA and permission boundaries

DATA separates local payloads from portable records: temporary inputs, research, assets, exports, and archives. Git ignores payloads by default; that does not establish privacy. Keep credentials out of records, select approved sources, and check actual permissions.

## 13. One workspace, multiple projects

A workspace can track software, research, operations, or channels as named System X P scopes. Each owns its context, plan, tasks, memory, and evidence while sharing reviewed outer tools. Reference shared requirements explicitly; do not import another project’s private memory.

## 14. Current setup locations

Current setup profiles cover projects, directories, drives, and chat. An existing client can synchronize a local Drive folder. System X supplies record and access guidance, not a cloud connector. Coordinate one writer per scope, retain source revisions, and inspect actual readback.

## 15. Measure the context budget

In this constructed fixture, a full-history resume used seven thousand four hundred seventy-five input tokens. System X used one thousand eight; an ordinary compact handoff used three hundred ninety-six. Setup and readback add eight thousand five hundred forty-seven tokens for System X, so first use costs more. On a tiny one-step task, tracking also used more context. These are named-tokenizer text counts, not measured bills, model quality, or speed. The useful comparison includes overhead and the work you actually need.

## 16. Adopt reviewed defaults, keep project records

Use the CLI, shell launchers, or Python library. Review and pin a release. Ordinary updates add defaults while preserving adopted files. Opted-in startup checks only notify. Controlled bootstrap refresh is separately backed up. Logged uninstall and restore retain a recovery path.

## 17. Inspect the recorded state

Inspect the implemented tools before trusting a result. Status, validation, task readiness, and bounded packets expose the recorded state. Format validation does not prove an application works. The included provider-free walkthrough exercises local record transitions without starting a model or claiming a real remote job.

## 18. Begin with a small pilot

Start with one project, one accepted outcome, and a reviewed version pin. Measure total resource use against your current workflow. Dot System X is public MIT alpha software. Read the wiki, watch the introduction, and adapt its generic records.
